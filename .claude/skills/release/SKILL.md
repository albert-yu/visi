# Releasing visi

Releases are **tag-driven**. `cargo release` bumps the versions, makes the commit
and writes the tag; **pushing the tag is what starts everything else**. Nothing
is released until `git push --follow-tags`.

The full flow is two commands (see "Cut it" below). The rest of this file is the
checks on either side and the things that are easy to get wrong.

## Before bumping

- On `main`, clean tree, in sync with `origin/main` (`git fetch && git status`).
- `cargo test --workspace --exclude visi-python` passes. (Drop `--exclude` only
  if a `python3` is on PATH; without one the pyo3 crate fails to link.)
- CI on `main` is green.

## Choose the level

Ask the user which level unless they already said. The project is 0.x, so a new
user-visible capability is a `minor`; a fix-only run is a `patch`.

`visi-core` and `visi` carry **independent version numbers** (see the comment in
`visi-core/Cargo.toml`) but should be released **together**: only a `visi` tag
starts the pipeline, so a lone `visi-core` bump ships nothing until the next
release. cargo-release handles the coupling — a `visi-core` bump rewrites the
requirement in *both* `visi/Cargo.toml` and `visi-python`'s **aliased**
`visi_engine = { package = "visi-core", ... }`. The aliased one is exactly what a
hand-edit or an obvious `sed` misses, and `publish-crates.yml` fails the release
on it. Do not edit the versions by hand.

`visi-python`'s own version is not bumped: it is `publish = false` and is not on
crates.io.

## Cut it

```bash
cargo release <level> --workspace              # dry run; prints every edit it would make
cargo release <level> --workspace --execute    # bumps, updates Cargo.lock, commits, tags
git push --follow-tags                         # this is what starts the release
```

Read the dry run before executing. It should show: the workspace version, the
`visi-core` version, both dependency requirements, and a single `v<version>` tag
(one tag, not per-crate, since both crates land on the same version).

If `--execute` is refused by the permission classifier, don't reconstruct it as
hand edits plus `git commit`/`git tag` — ask the user to run the two commands
themselves by typing them with a leading `!`.

`release.toml` sets `publish = false` and `push = false` **deliberately**: CI
publishes (doing it from a laptop would upload before the tag was pushed and
race the CI job), and the manual push leaves a beat in which a bad bump can be
amended rather than chased with a yanked release. Don't "fix" either one.

The release commit comes from cargo-release's own template (`Release
{{version}}`), so it carries no trailers. Don't amend it after the fact — the
tag would stay on the pre-amend commit.

## What the push starts

- **`release.yml`** (generated by dist): builds the seven target triples, cuts
  the GitHub Release with generated notes, and pushes the formula to the
  `albert-yu/homebrew-tap` repo.
- **`publish-crates.yml`** (a dist custom publish job, runs after the Release
  exists): first checks that `visi`'s requirement matches `visi-core`'s version,
  then publishes `visi-core` and `visi` in that order — `visi-core` has to be on
  the registry before `visi`'s verification build can resolve it. It skips any
  version already on crates.io, so it is idempotent.

## Watch it, and recover

```bash
gh run watch                          # the run just started
gh run list --workflow=Release
```

If the crates.io half fails on its own (expired token, registry down) but the
GitHub Release is fine, re-run just that half from the Actions tab or with
`gh workflow run publish-crates.yml` — it takes a `dry-run` input for a
package-and-verify pass, and skips whatever is already published.

Never move or re-push an existing tag. If a released version is wrong, bump
again and release a new one.
